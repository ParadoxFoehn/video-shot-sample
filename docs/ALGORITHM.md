# 算法说明：为什么这样选帧

> 这份文档解释「凭什么这样抽帧」，以及每个设计选择背后的实测依据。
> 只想用工具的读者看 `README.md` 就够了。

---

## 一、第一性原理：成本不对称

**人看视频不花钱，模型每读一帧都要付 token。**

| 对观众 | 对模型 |
| --- | --- |
| 连续镜头可以一直盯着看 | 每多给一帧就多一份成本 |
| 过程越连续越舒服 | 过程越连续越**不需要**给帧（能推断） |

所以判据不是「这一段重不重要」，而是：

> **这一帧能不能被两侧的帧推出来？**
> 能推出来 → 一帧都不给；推不出来 → 给一帧。

这条决定了后面所有设计：采样密度、张数预算、合并规则。

---

## 二、状态的边界在哪

### 2.1 镜头之内：连续 → 可推断

人物走路、镜头平移、光线渐变：中间帧可以由首尾帧线性插值近似出来。
**这类信息不需要逐帧看。**

### 2.2 镜头切换：不连续 → 必须给

场景变了、时间跳了、人物换了。这是**无法从上下文推断**的信息。
所以基本规则是「一镜一帧」。

### 2.3 镜头之内还可能有更细的状态变化

实测反例：一条 127 秒 MV 的 30.6 秒处，**同一个镜头里插了一条 1 秒的广告**
（淡入淡出）。切点检测只抓到它的出场（31.87 秒），没抓到进场（约 30.9 秒）。
于是「天台 → 广告 → 天台」被当成一个镜头，取 45% 处正好落在天台。

**结论：镜头不是唯一的状态边界，还需要第二路判据。**

---

## 三、两路判据，缺一不可

| 判据 | 抓什么 | 漏什么 |
| --- | --- | --- |
| 切点（ffmpeg `scene`） | 硬切 | 不到 1 秒的软过渡 |
| 像素差（灰度平均绝对差） | 晃动、闪光 | 画风渐变 |
| **颜色直方图（8×8×8 RGB，总变差）** | **画风/内容突变** | 颜色相近但内容不同的切换 |

### 实测：为什么必须加直方图

同一段素材，26–34 秒的两条曲线：

```
时间      像素差              颜色直方图
27.50s    68.23  ←全段最大    0.492
30.25s    54.89               0.595  ←全段最大（插播进场）
```

像素差的最大值落在**一次镜头晃动**上；直方图的最大值落在**插播**上。
只按「变化最大」选帧，插播永远选不到。

> **教训：像素差异是测量，信息差才该花 token。**

## 四、选帧五步

```
① 状态点先占位   直方图峰值处取「变化后 0.35 秒」
                 最多占一半预算，彼此 ≥2.5 秒
② 保首尾         整片开头结尾各一帧，否则补点循环算不出空档
③ 覆盖优先       从最大空档开始补点，补在区间内「像素差峰值」处
                 峰值太偏（不在 40%–60% 之间）且不够强 → 退回中点
④ 价值填满       剩余预算给「变化大且离已选帧远」的候选（score = dpx × √距离）
⑤ 近邻合并       间距 <0.6 秒视为同一状态，只留一个
```

### 为什么「状态点后 0.35 秒」

变化瞬间那一帧往往是过渡帧（模糊、叠化一半），**后移 0.35 秒**取到的是新状态的稳定画面。

### 为什么状态点最多占一半预算

全都给状态点，覆盖就没了：实测出现过最大空档 24.8 秒的版本。
现在强制留一半预算做覆盖，最大空档降到 7.2 秒。

### 为什么补点要平衡

早期实现把补点放在区间内的变化峰值处。峰值常偏在区间一端，结果洞被切成一大一小，
越补越不均：24 帧吃完仍有 9 秒空档。现在要求峰值落在 40%–60% 区间，否则退回中点。

## 五、三个实现事故（承接上文）

### 事故一：先补点、后抽稀 → 抽出更大的洞

旧流程「补中点 → 等距抽稀到目标帧数」，抽稀把刚补的点删掉。
实测空档 **13.24 / 12.39 / 9.74 秒**，全超过 8 秒上限。
→ 改成「先保覆盖、再按价值加帧」。

### 事故二：补点时反复插同一个位置

峰值点离已有帧太近时会回退到「中点」，而每次算出的中点**都一样**：
预算被吃掉，集合却没变大。这就是「24 帧有空档、40 帧却没有」的真正原因。
→ 回退时按 1/2 → 1/4 → 3/4 依次退让，插不进就跳出循环。

### 事故三：固定阈值从来没有生效

早期把「相邻镜头画面差 < 7 判同场景」写死。实测这条片子 60 对相邻镜头，
**最小 17.8 / 中位 53.9 / 最大 160.4**，全都大于 7——合并规则一次都没触发过。
→ 阈值改成按素材自适应（取分位数），并在启动时打印出来。

> **通用教训：规则「跑通了」不等于「生效了」。要打印中间量。**

## 六、和「声音那一路」怎么拼

本工具只处理画面。完整的「看懂一条视频」通常还要三样：

| 层 | 工具 | 拿到什么 |
| --- | --- | --- |
| 画面 | 本工具 | 状态帧 + 时间戳 |
| 台词 | whisper / MOSS 等转写 | 逐句文字 + 时间戳 |
| 声音 | BPM / 节拍 / 踩拍率 | 节奏与有无音乐 |

对齐方法：把三者的时间戳放到同一条轴上，**对上了才敢说因果，没对上就分开陈述**。

例：101 秒画面「她倒下」，歌词正好是「So let me down」——这才叫同步。

## 七、为什么不做「按运动量」

初版奖励「动得多」：运动活跃 98% 就给高密度。结果连续高速段拿走大部分预算——
**可那恰恰是最容易推断的部分**。反过来，一次切镜只动一瞬，信息量却最大。

同理，「按像素插值误差」也不行：像素级「推不出来」不等于语义上「不知道发生了什么」。
实测那条 MV 用插值误差选帧，61 帧里 40 多帧挤在最后 17 秒的快剪段落。

## 八、参数与实现对照

| 参数 | 代码位置 | 影响 |
| --- | --- | --- |
| `--max` | `build_plan()` 的 budget | 决定最终帧数与 token |
| `--max-gap` | 第 ③ 步循环条件 | 空档上界 |
| `--hist-threshold` | 第 ① 步 `thr_h` | 判为「状态变化」的灵敏度 |
| `--cut-threshold` | `detect_cuts()` | 切点数量 |
| `ANALYZE_FPS` | `decode_features()` | 分析精度与耗时（默认 4） |
| `FEAT_W/FEAT_H` | 同上 | 特征分辨率（默认 64×36） |
| `TOK_PER_SHEET` | 常量 | token 估算口径（默认 224） |
